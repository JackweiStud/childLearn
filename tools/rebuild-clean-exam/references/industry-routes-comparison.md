## 一、4 条主流路线对比

| 路线 | 代表产品 | 优点 | 致命缺点 |
|---|---|---|---|
| **A. 图像 inpainting** | Magic Eraser (Google)、Lama Cleaner、Photoshop AI、Stable Diffusion + ControlNet | 保留原始视觉风格、自动化 | **AI 会幻觉**——被遮挡的数字/字母被 AI"猜"回来，100% 不能用于教育场景。1+1=2 可能被画成 1+1=3 |
| **B. OCR + 重排版** | OneNote 扫描、PaddleOCR pipeline、Tesseract pipeline | 全自动、批量、零成本 | 中文 + 数学符号 OCR 错误率 10-30%；图形（钟表、方格、坐标系）**完全丢失**；版式失真 |
| **C. 商业 OCR + 人工审核** | 教培行业题库系统、试卷扫描 SaaS | 工业级准确 | 人工成本 = 工业级；需要 API + 数据上云 |
| **D. LLM 视觉 + 矢量重建** ⭐ | **本工具走这条** + Mathpix（仅数学） | 准确度上限最高、保留图形、可审计 | 单题成本高、依赖云端 LLM、需要工程化（reportlab）|

**关键事实**：D 路线**没有商业最佳实践产品**——这个细分市场太小没人卷。Mathpix 是最接近的商业产品，但只覆盖数学，且约 $20/月、要 API key、数据要上云。

## 二、各路线深入

### A. 图像 inpainting：为什么不能用于教育

inpainting 的工作原理是「看着像」——AI 根据上下文像素分布预测被遮挡的内容。

- **风险点**：题面里的数字 `8` 被笔迹覆盖一半 → AI 看着像 `6` 就画 `6`。**1+1=8 可能变成 1+1=6**，孩子学错。
- **业余尝试常见错误**：把"清除笔迹"理解为 Photoshop 涂白 → 看着干净但内容已毁。SKILL.md 第 17 行的"重建 ≠ 修复"原则正是对此的反共识判断。
- **唯一可用场景**：纯视觉装饰（如试卷边角的污渍），不涉及题目内容。

### B. OCR + 重排版：丢图形是致命伤

- 现代 OCR（PaddleOCR、Tesseract、百度 OCR API）对**印刷中文 + 印刷数字**已经接近 95% 准确
- 但**手写残留**会污染识别；**数学符号**（`±`、`÷`、`²`、`√`）和**版式**（题号缩进、空答题线、应用题图）大概率丢失
- **二年级数学的关键内容**——钟表、数轴、方格图、计数图——OCR 全部失败，必须重建

### C. 商业 OCR + 人工审核：成本不可承受

教培行业题库扫描 SaaS（如腾飞 OCR、合合 OCR）做这套：
- OCR 抽取 → 后端审核员逐题校对 → 入库
- 单题人工审核成本几元，规模化才划算
- 对个人家长场景，**人工审核成本 = 自己重做一遍**

### D. LLM 视觉 + 矢量重建：本工具的路线

- **流程**：LLM（Claude 4.7 / Gemini 2.5 / GPT-4o）看图 → 提取语义到中间模型 `questions.json` → reportlab 矢量重绘 → 输出 PDF
- **质量上限**：LLM 视觉 + 人工审 + 矢量重绘，理论上能达到 100% 准确
- **成本下限**：单题 LLM 调用 + 1-5 分钟工程化
- **可审计**：`questions.json` 带题级 `source` + `confidence` 标记（5 种来源 / 4 种置信度），出错可定位

## 三、本工具的设计判断（why D）

### 选 D 的真实原因（按 Jack 的具体约束）

- **场景**：单孩子、单家庭、每天 1-3 道错题
- **质量要求**：100% 准确（错了误导孩子）
- **A/B 因质量天花板出局**
- **C 因成本 + 数据上云出局**
- **D 路线在 LLM 时代变得可承受**——3 年前这套不可行（GPT-3.5 视觉差），现在 Claude 4.7 视觉 + 工程化能跑

### 本工具的 3 个反共识但正确的判断

1. **重建 ≠ 修复**（SKILL.md 第 17 行）—— 业界主流 inpainting 工具的反向选择
2. **「待确认」作为兜底**（SKILL.md 第 25 行）—— 遮挡且推不出来时拒绝出答案、请用户补拍。业界默认会幻觉一个
3. **可审计中间层 `questions.json`** —— 业界主流是端到端黑盒；本工具中间产物可审计、可重跑

## 四、本工具与"理想最佳实践"的差距

`✓` = 业界做了 / `✗` = 业界没做 / `?` = 业界做了但本工具没

| 维度 | 业界严肃产品 | 本工具 |
|---|---|---|
| 重建 ≠ 修复哲学 | 部分有 | ✓ |
| 待确认兜底 | 极少 | ✓ |
| 可审计中间层 | 极少 | ✓ |
| 字体加载工业化（subfontIndex + magic 自检）| ✓ | **✓（2026-06-29 补完）** |
| 题级强校验 | ✓ | **✓（2026-06-29 补完）** |
| **Cross-LLM 验证**（2 个独立 LLM 复核）| ✓（金融/医疗 OCR）| **? 未做** |
| **Ground truth 回流**（人工修正回流为 few-shot）| ✓ | **? 未做** |
| **LLM 直出 SVG/LaTeX** 替代 reportlab | 新兴 | ? 未做（trade-off：可控性 > 效率）|

### 3 个真实改进点（不该现在做）

1. **Cross-LLM 验证**：当前 Claude 单点判断，错了无察觉。加 Gemini 2.5 复核，不一致进 ambiguities。**ROI**：质量提升明显，成本翻倍。
2. **Ground truth 回流**：用户每次手工修正后，回流为 few-shot example。下次同类题型直接命中。**ROI**：积累期收益小（错题样本少），积累后期收益大。
3. **LLM 直出 SVG/LaTeX**：替代 reportlab 手工堆叠。**ROI**：效率高但可控性下降；当前 reportlab 路线的确定性是工程价值，不该轻易换。

## 五、判断与决策原则

**真实结论**：

- **不是业界最佳实践**——业界没有这个细分市场的最佳实践
- **比业界主流路线（A/B）合理**——质量上限决定的
- **比业界商业方案（C）适合 Jack 场景**——成本和数据自治

**按 CLAUDE.md「积累期」原则，本工具应当 freeze**：
- 错题归档攒到 20+ 之前不做新功能
- 看到真实的"哪一类题最容易翻车"再决定优化哪条
- 不要在没看到真实痛点之前空想架构升级
